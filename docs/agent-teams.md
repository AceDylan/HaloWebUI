# 协作台（Agent Teams）

HaloWebUI 里的多代理协作：一位负责人（team-lead）拆分工，几位成员按依赖并行/接力完成，整个过程在同一个网站里看得见、管得住、能回放。执行仍由 Hermes 和现有 runner 负责，没有新客户端、新登录或新服务。

## 怎么用

- **入口**：侧栏「协作台」（/teams）；或在聊天顶栏「···」菜单点「协作任务」（会关联当前对话，协作台里有「返回对话」）。
- **在对话历史里**：每个协作任务都是一段对话，和精答、讨论一样出现在侧栏的对话历史里（带「协作」标记），并按普通对话的规则自动归到合适的对话分组：
  - 在协作台（或 Telegram）单独发起的：建一段自己的对话——你写的目标（不含带过来的背景）+ 一张实时进度卡片，标题跟着负责人给计划起的名字（你改过名就不动）。
  - 从对话发起的（「···」菜单、把草稿交给协作台）：目标和进度卡片接在那段对话后面（对话正在回答时不插，结果照样发回来）。
  - 派发方式「协作台」：那条消息的回复就是卡片（原来就这样），现在也会像普通对话一样归组。消息以 `/命令` 开头时交给 Hermes，不建团队；临时对话不能派发。同一个弹窗里还有精答、讨论，见 [hermes-dispatch-modes.md](hermes-dispatch-modes.md)。
  - 以前的协作任务：第一次打开列表时补上对话，按任务当时的时间排在历史里（不挤到最上面）；最近 20 个会自动归组。删掉的对话不会再建。
  - 团队在干活时，历史里它的对话有蓝色呼吸点；计划等你批准或有事要你处理时是紫色点。打开协作台、结论页时，历史里对应的对话是选中状态。
- **对话里的卡片**：成员头像、负责人 + 几位成员 · 几个任务 · 在哪个项目 · 附带几个文件；进行中显示阶段条（和协作台同一条），等批准/要处理时按钮直接是「去批准」「去处理」。完成后：结果已经发回这个对话就「看结果 ↓」跳过去，还没发回（比如以前的任务）就「把结果放进这个对话」；下面是「结果页 · 产出文件 · 过程记录」。协作台删掉的任务，卡片只留一行说明，对话和结果都还在。
- **发回对话的结果**：结论是一条完整回复，末尾一行「在协作台看：结果页 · 产出文件 · 过程记录」在页面上显示成按钮，**都在当前页打开**（不再新开标签页），浏览器后退回到对话；`#files`、`#process` 直接落到结论页的「产出文件」和展开的「过程记录」。对话里所有指向本站页面（/teams、/discuss、/answer、/c …）的链接都在当前页打开，外部网站和文件下载照旧新标签页。结论页右上角「← 回到对话」。
- **发起**：写下目标 → 负责人做计划（一次模型调用，不启动任何成员）。
- **在哪做**：输入框下的「在哪做」——「自动」（目标里点名了某个项目，比如「给 HaloWebUI 加…」，就在那个项目里做）、「新目录」、或直接选一个项目（本机的 git 仓库：HERMES_DISPATCH_PROJECTS 里的和最近 runner 干过活的目录）。在项目里做时，批准后团队从项目当前的提交开一个自己的分支 `halo/<看板>`，在独立的 worktree 里改，**不碰你正在用的工作区**；每个任务完成自动提交一次。审批页写明在哪做，可以「改在新目录重做计划」或「换到项目里重做」。
- **变更**（项目团队才有，工作台「结论」旁边的标签）：团队分支、按任务的提交、改动的文件（+/−，点开看差异）、还没提交的文件。团队完成或停止后可以：「合并到 main」（要求你的工作区没有未提交的改动；能快进就快进，否则生成合并提交；冲突会撤回并告诉你）、「推送团队分支」、合并后「推送 main」（会触发这个仓库推送后的自动构建/部署）、「放弃分支」（删 worktree 和分支，结论保留）。都要你点，团队自己不会推送；成员被要求不 push、不切分支、不合并主分支。结论只列团队改过的文件，负责人写结论时拿到完整的改动清单。
- **审批**：看成员分工、按依赖分层的任务、预计同时执行人数（本机上限 2）。负责人用的是 Hermes 当前的默认模型（`model.default`，现在是 gpt-chat，调用时实时读取；它不可用时按 Hermes 的备用模型兜底），页面会写明是哪个模型做的计划。
  - **角色 = 助手模板**：负责人优先从 HaloWebUI 的助手模板里给每个成员选角色（模板页「协作」分组里的那些，如 开发工程师、前端工程师、代码审查员、技术写作专家），成员执行时把模板当作角色设定；没有合适模板时写「自定义角色」。
  - **执行来源（runner）与角色无关**：每个成员有一个任务类型，按类型自动推荐 runner——后端 / 通用代码 → cchclaude，前端 / UI / UX / 视觉 → agy，复杂任务 → reclaude 起，调研 / 写作 → Hermes。推荐的 runner 不可用时沿 **reclaude → cchclaude → anyclaude → codex → agy → hermes** 从推荐的那个往后兜底，页面写「实际将由 X 执行 · 原因」。
  - 可以手动改任何成员的执行来源（「你手动指定」，自动策略不会改回去；它不可用时同样往后兜底并写明）；「恢复自动」回到按类型推荐。下方「执行来源」面板显示每个 runner 现在能不能用、卡在哪一层，可以「重新检测」。
  - 然后「批准并开始」「按意见重新规划」或「取消」。普通聊天不会自动启动多代理。
- **工作台**：
  - 成员条：负责人和每位成员现在在做什么（执行中 / 等待派发 / 等待前置任务 / 等你回复 / 额度等待 / 失败 / 已停止 / 已完成）。
  - 依赖任务板：一列一个依赖深度，并行任务上下排列；实线 = 前置已完成，流动虚线 = 前置执行中，灰虚线 = 还在等；等待中的任务写着在等谁。点任务看详情。
  - 通讯与日志：成员留言、完成交接（交给谁）、你的补充说明及其送达状态、工具记录、状态变化。全部来自真实记录。
  - 详情：任务说明、执行来源（默认 → 实际，以及每次改派的时机和原因）、每次执行尝试（runner 成员会列出对应的 runner 运行和续跑关系）、结果（按 Markdown 显示）、按需加载的日志；可以给该成员补充说明、重试失败的任务（重试时重新从首选执行来源开始选）。
  - **结论**：通讯栏旁的「结论」标签（手机上是第四个标签）。所有任务完成后，负责人（同一个模型）根据每个成员的完整结果和工作目录里的文件写一份结论报告；团队完成时页面顶部出现完成横幅，结论标签自动打开。「全文阅读」打开独立的阅读页（目录、复制、下载 .md、重写）。报告里的 Markdown、表格、代码、JSON、图片（工作目录里的图片、图片链接都会直接显示）都按聊天同一套渲染器显示，下方列出产出文件和各任务的原始结果。负责人模型没回答时，结论按任务记录整理并如实标注；停止的团队可以手动「让负责人写结论」。
- **控制**（三件不同的事）：
  - 回放条的「暂停回放」只影响画面；
  - 「暂停派发」：不再开始新任务，正在执行的成员做完手上的；
  - 「停止执行」：结束正在执行的成员（runner 的运行会被停止），不会被自动恢复，也不能再继续。
- **回放**：从头回看，0.5/1/2/4 倍速，可拖时间轴；成员、任务板、统计和通讯都对应同一时点。回放只读已有记录，不会触发任何模型、工具、消息或重试。长时间没动静的间隔会被压缩。
- **手机**：同一页面换成「任务 / 成员 / 通讯」标签，不显示画布。
- **Telegram**（和 Hermes 同一个机器人）：
  - `/team 目标` 发起；负责人做好计划后发来计划卡片（成员、任务顺序、执行来源），点「批准并开始」或「取消」，或者直接回复卡片写修改意见让负责人重新规划；卡片发出后 30 分钟内直接发「批准」也行。`/team` 单独发 = 最近的协作任务。
  - 执行中：成员提问、任务失败/受阻、全部完成（附结论开头）会推送过来——TG 发起的团队推到发起的对话，网页发起的推到你绑定的 TG 私聊；**你正开着这个团队的页面时不推**（页面上已经看到了）。回复提问 = 回答成员；回复失败通知 = 补充说明并重试；失败通知上也有「重试」按钮。
  - 协作台列表和工作台标题旁的「Telegram」标记表示这个团队是在 Telegram 发起的。

### 补充说明什么时候送达

| 情况 | 送达方式 | 显示 |
|---|---|---|
| Hermes 成员正在执行 | 成员每 ≥6 秒检查一次，当前这批工具调用结束后读到 | 已送达（运行中注入） |
| 成员刚开工、读取任务时 | 任务评论本身就在它读到的内容里 | 已送达（成员读取任务时看到） |
| 任务还没开始 / 重试 | 随下一次执行尝试的上下文 | 已随新的执行尝试送达 |
| runner 成员（reclaude、codex 等）正在执行 | 不能中途收消息：它这一轮结束后，用同一会话续跑送达 | 已通过续跑送达 |
| runner 成员提问（QUESTION） | 你的回答直接交给同一会话续跑 | 已通过续跑送达 |

在送达之前一律显示「排队中」；任务结束前都没送达会显示「未送达（任务已结束）」。

## 架构

- **任务事实源 = Hermes Kanban**。每个协作任务一个看板 `halo-<id 前 16 位>`（`~/.hermes/kanban/boards/`）：任务、依赖、执行尝试、评论、事件都在 Kanban 自己的表里。派发器（网关内置）真正检查依赖：前置没完成的任务不会被领取。
- **归属与审批 = HaloWebUI `agent_team` 表**：谁发起、哪个对话、批准前的计划、对应的看板。所有接口按用户隔离（管理员也只看自己的）。
- **Hermes 插件 `halowebui-teams`**（本仓库 `integrations/hermes-plugin/halowebui-teams/`，见其 README）：`/v1/halo-teams` 接口（计划、建看板、快照、事件、详情、补充说明、暂停/恢复/停止、重试），worker 内的钩子（成员工具调用、原生子代理、说明送达），reclaude 执行桥接。
- **执行来源**：Hermes 成员由 Kanban 派发器以 `default` profile 启动（成员身份记在看板元数据里）；runner 成员（reclaude、cchclaude、anyclaude、officlaude〔官方 Claude〕、codex、agy）由插件桥接直接调用对应的 `<名字>-run.sh`（额度等待、提问、续跑、停止都按 runner 自己的语义映射），这些 run 不发聊天通知、不被 autopilot-supervisor 接管。runner 是一张数据表（插件 `runners.py`），角色是助手模板（`assistants.py` 读 `src/lib/data/agents-zh.json` 里「协作」分组和 `team_kind`），两者独立。
- **可用性与兜底**：每个 runner 分层检测——已配置 → 已安装（脚本 + 命令）→ 可执行（`--version`）→ 账号 / 额度（reclaude 拼车额度预检、cch/any 中转的模型列表、`codex login status`、agy 登录令牌）→ 网络可达 → 最近运行没有因额度 / 登录 / 地区 / 网络 / 命令缺失失败（30 分钟内）。结果缓存 120 秒。改派发生在四个时机：批准时、启动前、运行中（runner 因上述原因失败，或额度等待超过 20 分钟）、重试时；任务本身做错了不改派。每次改派记在任务的 trail 上并写进通讯记录。
- **结论**：插件 `conclusion.py`，团队完成后后台生成，存 `<工作目录>/.halo/conclusion.md`；工作目录文件经 `/api/v1/teams/<id>/files/<路径>` 读取（只限该团队工作目录、按用户隔离，HTML 按纯文本返回）。
- **实时**：页面可见时每 2.5 秒按游标增量拉事件，隐藏时 30 秒；断线自动退避重试、恢复后补齐；完成后停止轮询。事件带「事件后的任务状态」，回放就是按顺序折叠；历史与当前状态不一致时页面会明确说明。

## 开关与限制

- 关闭：HaloWebUI 环境变量 `ENABLE_AGENT_TEAMS=false`（接口 404、入口隐藏）；Hermes 侧从 `plugins.enabled` 去掉 `halowebui-teams` 并重启网关。
- runner 策略可选覆盖文件 `~/.hermes/halo-teams-runners.json`（改了立即生效，不用重启）：`{"order": [...], "kinds": {"code": "codex"}, "disabled": ["anyclaude"], "unavailable": {"cchclaude": "中转维护中"}, "quota_wait_max_seconds": 1200}`——`unavailable` 是手动维护开关，标记的 runner 会像真的不可用一样被兜底跳过。
- Telegram 联动：`~/.hermes/halo-teams.json`（`halowebui.url` 本机地址、`halowebui.public_url` 按钮里的网页地址、`telegram.owners` = {TG 用户 id: HaloWebUI 用户 id}、`telegram.notify_web_teams` 网页发起的团队是否也推送，默认开），改了立即生效；没有这个文件或没列出的 TG 用户，`/team` 等消息原样交给 Hermes。HaloWebUI 侧 `/api/v1/teams/hermes/*` 只认该用户 Hermes 连接里的同一把 API key。
- 负责人模型默认跟随 Hermes `model.default`；要单独指定，在 Hermes `config.yaml` 加 `auxiliary.halo_team_lead: {provider: ..., model: ...}`。
- 并发：`kanban.max_in_progress: 2`（全机，含 runner 成员）；同一种 runner 的成员同时最多 1 个（不同种类互不占用，比如一个 reclaude 加一个 codex 可以同时跑）。
- 已知限制：
  - 普通聊天里 Hermes 自己派出的子代理（delegate_task）仍显示在聊天的工具块里，不进协作台；协作台显示的是团队成员及其子代理。
  - 一个团队的成员共用一个工作目录（`/root/work/agent-teams/<看板>`；项目团队是那里的 worktree），计划要求并行任务写不同文件。所以项目团队每个任务的提交是「它完成时工作区里的改动」：整体 diff 准确，按任务拆分是尽力而为。
  - 计划批准前只能调整成员的执行来源，其余改动请「按意见重新规划」。
  - 停止是终态；暂停派发可以恢复。
  - 只有 reclaude / cchclaude / anyclaude 会在额度用完时自己等重置后续跑（页面显示「额度等待」）；codex、agy 撞上额度就是失败，等额度恢复后在协作台点重试。reclaude 的额度等待、自动续跑目前只用模拟 runner 验证过。
  - agy 的进度日志不记录工具调用，所以 agy 成员没有工具记录，只有开始/结束和结果。
  - agy 的账号 / 地区问题只能从它最近一次运行的失败里看出来（没有不花额度的探测），所以它出问题后的第一个任务会失败一次再兜底；之后 30 分钟内直接跳过它。

## 回滚

- HaloWebUI：`docker tag dylanha009/halowebui:rollback-pre-teams dylanha009/halowebui:custom && cd /root/halowebui && docker compose up -d`（`agent_team` 表留着无害）。
- Hermes：`plugins.enabled` 去掉 `halowebui-teams`，删掉 `config.yaml` 末尾的 `kanban:` 段（备份 `/root/backups/halo-teams-20261002/config.yaml.before`），`hermes gateway restart`。团队看板留在磁盘上，不影响其他用途。

成员执行来源可显式选择「官方 Claude」（officlaude，官网订阅 OAuth），角色不受限制。它不进入任何自动回退链，既不自动推荐也不自动接替其它来源；认证/订阅额度失败保留失败供用户处理后重试，不自动等待。

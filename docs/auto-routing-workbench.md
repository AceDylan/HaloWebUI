# 自动分流工作台

`/auto` 是独立入口，侧栏位于「新对话」下方，独占一行；精答、讨论、协作、生图保留原来的模式行。顶部模式切换条和命令面板也可进入。切换入口时携带已上传附件、草稿和背景。

## 行为

- 输入问题和最多 4 个附件，自动选择精答、讨论或协作；也可手动指定。
- 自动分类优先使用当前用户可访问的 `gpt-chat`（兼容连接作用域模型 ID），其次使用管理员配置的可用外部任务模型，最后使用精答调度模型。分类限时 25 秒；失败或格式不可用时默认精答。模型清单读取等外围步骤限时 60 秒。
- 精答复用原有助手匹配和按需联网。讨论使用独立的单轮对照设置，标准最多 3 席，精简 2 席；不会沿用上次重型讨论设置。
- 分流依据是「哪种方式能明显提升结果」，不是「是不是咨询」：是什么、怎么用、适合什么场景、简单推荐 → 精答；有合理的不同方案且取舍会改变结论（结合自己的条件选哪个、找方案漏洞、定优先级/权限边界/架构，或用户点名讨论）→ 讨论；复杂或需要最新信息本身不算讨论理由。两条判定路径（默认分类模型的提示词、辅助决策模型的选项说明）共用同一组边界示例 `EXAMPLES`。
- 「需要工具」和「允许修改」分开判断：分类结果带 `needs_tools`（要看真实仓库/文件/配置/日志或运行命令才能如实回答，读附件不算）和 `execution_requested`（明确要求现在创建、修改、运行、交付）。需要工具但没有执行请求，或用户说了「只分析/只看/不要修改」，交给**只读协作**：协作目标里追加只读约束（不建、不改、不删文件，不提交、不推送、不部署，不运行改变状态的命令），卡片和对话里显示「协作台（只读）」。只读约束写在任务里交给执行者，不是工作区层面的强制隔离。
- 协作还需要可用的 Hermes 连接和开启的协作功能。默认先出计划，用户勾选「协作计划后直接开始」才允许自动启动（只读协作同样适用）；从对话派发时计划在对话卡片里直接批准。只分析等约束优先；明确的新执行请求可覆盖之前一轮的只分析要求，一句「继续」不算授权。
- 追问按自己的意图重新判断（对话里每条消息都重新分流）：「介绍两种数据库」→ 精答，追问「结合我的业务选哪个」→ 讨论，再说「按方案实现」→ 协作。
- 正常选择和临时改用分开：讨论模型不足、协作不可用、分类失败时，记录带 `degraded`（原本想用的方式，分类失败为 `auto`），卡片和结果页显示「临时改用」，对话回复写「🔀 自动分流临时改用精答：…」。需要查真实文件但协作不可用时**不降级**：记录 `status=error` + `blocked=true`，卡片显示琥珀色「已阻塞」，对话回复改为「⛔ 自动分流没有派发：…」，用户可在卡片里改选精答只要一般建议。
- 「只分析」只认整体性的约束：只分析/仅评估/不要执行/不要动手/不要修改（任何文件、代码）/先出方案（后面没有「再修复…」）/analysis only。只禁止某个动作的（「不要部署」「不要修改数据库」「don't deploy」）是任务约束，跟着任务一起交出去，不再把「修复并测试，不要部署」判成只分析。对话背景里只看「用户：」说的话，助手说的「我先分析一下」不算用户的要求。
- 关闭联网对精答和讨论直接关闭检索，对协作作为任务约束传递给执行者（不是独立的工具网络隔离）。协作目标和背景合计超过既有 8000 字上限时提示精简，不截掉约束。
- 结果仍在 `/answer/{id}`、`/discuss/{id}`、`/teams/{id}`，顶部显示分流理由。最近记录查询服务器端记录，目标任务删除后标记已删除。历史按 `(created_at, id)` 游标翻页，每页 30 条，前端只保留当前页；支持服务端问题搜索与模式筛选，后端批量读取目标标题/状态，不读取整段聊天内容。
- Hermes 输入框的「派发给谁」有「自动分流」，结果卡片显示在原对话。侧栏同时显示「自动 · 精答/讨论/协作」，原对话复用智能标题与自动分组；打开旧版自动分流卡片时按需补齐遗漏的标识、标题和分组，不扫描全部聊天。手写 `/命令` 优先，普通续接仍遵守原有 runner 续接逻辑；聊天自动协作先出计划。

## 共享标题与回填

「智能生成 → 对话标题」的开关、任务模型和提示词统一用于普通对话、自动分流、精答、讨论、协作台及生图记录。派发不等待标题生成；后台最多等待 60 秒，失败用问题摘要兜底。用户手动命名和已切换的对话分支仍受保护。生图通过 `/api/v1/image-studio/items/title` 调用相同服务（最多 25 秒，使用外部文本任务模型），一组图片及历史共用一个标题，保留完整原始提示词；生成期间删除的记录不会被重建。

从对话派发的精答/讨论不再由子任务提前弹出完成通知。结果回填后保存消息 ID，卡片同时核对本地聊天和服务端回执；已完成但尚未同步时显示同步状态，提供「重新同步结果」。协作卡片同样使用服务端回执，点击结果可定位消息或打开结果页。

本次不新增数据库迁移；标题、自动标识及回执使用既有 JSON 字段。回滚应用后新字段可保留，旧版本忽略它们。

## 持久化和恢复

首次上线时新增 `auto_route` 表，迁移 `a7d93e5f8102`，前序为 `b8e4c2a7d913`。每个用户的 `client_key` 唯一，持久化输入摘要、输入、选择理由、目标和状态。相同键不同输入返回 409；断网后同键重试复用记录。

状态为 `routing → dispatching → dispatched`，另有 `cancelled / error / interrupted`。目标创建后、启动之前立即记录目标 ID。只允许在 routing 状态取消，取消与派发由条件更新仲裁。后端重启后不会自动重做不确定的派发；超过 10 分钟未更新的请求标为中断，已记录的目标仍可打开。极端情况下进程在目标插入和绑定回执之间退出，需要人工核对已有任务，原请求不自动再派发。

对话里的那条回复在选定方式后改写成「🔀 自动分流交给了协作台：<理由>。进度在下面的卡片里…」（Hermes 下一轮读到的也是这句）；旧回复还停在「正在选择处理方式」的，打开卡片时顺带改正。改写和重试都不移动对话的当前消息（`set_current=False`）。结果页顶部的提示带「回到原对话 →」（从 /auto 发起的是「分流记录 →」）。

派发失败、中断或取消的请求可以在对话卡片里「重新分流」，或直接交给精答/讨论/协作（`POST /api/v1/auto/{id}/retry`，`mode` 可选）：沿用原输入和来源对话、重新校验附件，生成新回执，原消息的卡片改指向新回执；连按两次复用同一个新回执，不会派发两次。

`POST /api/v1/auto/` 提交，`GET /api/v1/auto/` 用 `before=时间戳:ID` 分页列出（兼容旧 `offset`，`q` 搜索问题、`mode` 筛选），`GET /api/v1/auto/{id}` 恢复，`POST /api/v1/auto/{id}/cancel` 取消选择，`GET /api/v1/auto/target/{mode}/{id}` 供结果页显示理由。全部接口按登录用户隔离。附件验证归属后才创建请求。

## 发布与回滚

推送 main 后由现有 GitHub Actions 测试并构建 `dylanha009/halowebui:custom`，部署由管理员拉取更新。升级启动时执行数据库迁移；部署前按既有流程备份数据库。

回滚应用使用上一镜像。新增表与旧功能独立，可保留分流记录；确需撤销数据库迁移时，在备份后回退到 `b8e4c2a7d913`，会删除分流回执，不删除已创建的精答、讨论和协作任务。取消分流不等于取消已启动的目标任务，目标任务使用各工作台的停止功能。
